# KotoMachi를 만들며

KotoMachi는 가을 삿포로를 걷고 일본어를 쓰는 작은 RPG로 시작했다. 실행 환경과 학습 구조, 화면을 고쳐 가며 첫 시제품은 Chapter 1 전체로 확장됐다. 마지막에는 등장인물의 일본어 대사에 음성까지 입혔다. 이 글은 Chapter 1의 제작을 마치기까지, 저장소의 문서와 커밋에 남은 선택과 시행착오를 따라간다.

## 한 장면에서 시작한 프로젝트 {#beginning}

2026년 9월 23일의 첫 기획 문서에는 가을 삿포로, 반복해서 만나는 사람들, 이야기 속 일본어 학습이 함께 등장한다. 게임 콘셉트와 학습 설계, Chapter 1의 이야기와 지도를 계획한 뒤, 역 앞에서 안내 직원과 대화하고 저장·이어하기를 확인하는 작은 시제품을 만들었다.

첫 구현은 React Native 기반으로 Apps in Toss를 대상으로 했다. 한 장면에서 일본어 대화와 단어 도움, 음성 재생을 시험했지만, 실제 Toss iOS·Android 호환성은 아직 확인하지 못한 상태였다.

기기 TTS로 일본어를 읽는 방법도 검토했다. 다만 Toss에서 사용할 경로가 확인되지 않아, 첫 시제품에는 미리 생성한 음성 파일을 넣었다. 음성 구현은 이후 플랫폼 전환과 함께 다시 바뀐다.

:::human-note
게임을 만들게 된 계기는 거창하지 않다. 여러 AI Agent를 이용해서 웹 시스템이나 자료는 만들어봤지만, 좀 더 복잡한 시스템에 도전해보고 싶었다. 그중 생각한 것이 '게임'이었고, 마침 아내가 하던 일본어 공부 게임의 엔딩이 나버렸다.

AI 시대에서 SW는 이제 더 이상 소수의 전유물이 아니었고, 누구나 원한다면 자신만의 SW를 만들 수 있는 세상이다. 나 또한 우리 가족에게 필요한 SW를 직접 만들고자 했다. 대단한 수익 창출이나 성공을 기대하기보다는, 살면서 한 번도 접해보지 못했던 '게임 기획 및 개발'이라는 경험을 바라보며 기존 게임의 기본 콘셉트만 참고했다. 특히 기획 초기에는 어린 시절 좋아했던 포켓몬스터 게임의 경험에 일본어 공부를 더하고자 생각했었다.
:::

## 실행 환경을 다시 고르다 {#platform}

첫 시제품 이후에는 실행 환경부터 바꿨다. 9월 25일 인프라 문서가 PWA 우선 방향으로 바뀌었고, 설치 가능한 웹 앱이 구현됐다. 이후 KotoMachi는 React, TypeScript, Vite 기반의 브라우저 게임으로 개발됐으며, 현재 Vercel에 배포되어 있다.

인프라 문서는 빠른 배포와 재사용을 이유로 든다. 네이티브 전용 기능이 필요하지 않은 단계에서, 웹은 HTTPS로 바로 배포하고 iPhone 홈 화면에 설치해 시험할 수 있었다. 나중에 Apps in Toss WebView에서도 같은 빌드를 재사용할 수 있다. 우선 브라우저에서 게임을 만들고 확인한 뒤, 배포 채널을 넓히는 선택이었다.

저장도 서버 없이 기기 안에서 처리하는 local-first로 시작했다. 계정과 클라우드 동기화를 운영하지 않고, 진행 데이터를 브라우저의 IndexedDB에 보관한다. 대신 기기 간 저장 이동은 보장되지 않고, 브라우저 데이터를 지우면 진행을 잃을 수 있다.

챕터가 커져도 기존 플레이를 이어 갈 수 있도록, 저장 형식이 바뀔 때 데이터를 변환하고 복구 사본을 남겼다. 앱 파일은 Workbox로 캐시하고 업데이트 전에는 진행을 저장한다. 저장 공간이 웹 주소의 출처(origin)에 묶이므로 배포 주소도 유지한다. 첫 버전의 운영 범위를 줄이면서, 반복 배포가 플레이 기록을 끊지 않게 한 구조다.

### 01. React Native 시제품에서 PWA로 방향을 바꾼 이유

첫 개발 목표에는 **Apps in Toss 안에서 실행되는 모바일 게임**이 있었다. 2026년 9월 25일의 첫 수직 시제품은 React Native 기반으로 역 앞 한 장면과 일본어 대화, 저장·이어하기를 검증했다. 그러나 이 단계에서 실제 Toss iOS·Android 기기의 호환성이 확인된 것은 아니었다. 한 장면을 만드는 데 성공한 것과 그 환경을 Chapter 1 전체의 기반으로 선택하는 것은 다른 문제였다.

인프라 방향은 같은 날 **PWA 우선**으로 전환됐다. 코토마치처럼 2D 화면, 터치 입력, 대화, 로컬 저장이 중심인 게임은 브라우저에서도 핵심 경험을 먼저 구축할 수 있었다. React·TypeScript·Vite로 만든 웹 빌드를 Vercel에 배포하고, iPhone에서는 홈 화면에 설치하는 방식을 택했다. Apps in Toss는 버린 목표가 아니라, 필요할 때 별도 검증을 거쳐 연결할 **추후 배포 채널**로 남겨 뒀다.

### 02. 서버를 만들지 않고도 게임이 이어지는 구조

현재 게임은 접속자별 계정이나 진행 데이터를 저장하는 백엔드 서버 없이 동작한다. **GitHub의 소스 → Vite 정적 빌드 → Vercel 배포 → 각 사용자의 브라우저에서 실행**되는 구조다. 게임 콘텐츠와 실행 코드는 배포하고, 각 플레이어의 진행 상태는 그 사람의 기기에 남긴다.

이를 위해 게임 로직은 플랫폼 구현에 직접 의존하지 않도록 `SaveService`, `SpeechService`, `AudioService` 등의 경계를 뒀다. 지금은 PWA용 구현을 사용하지만, 다른 실행 환경으로 옮겨야 할 때에는 게임의 스토리·퀘스트 로직을 통째로 다시 쓰기보다는 해당 기능의 연결 방식을 교체할 수 있도록 설계한 것이다.

### 03. IndexedDB: 자동저장보다 어려운 것은 기존 세이브를 지키는 일

실제 진행 데이터는 브라우저의 `IndexedDB`에 저장한다. 데이터베이스 이름은 `kotomachi-pwa`, 저장소는 `saves`, 사용자가 보는 세이브 슬롯은 `primary` 하나다. 퀘스트 진행도, 인벤토리, 학습 상태, 위치처럼 이어하기에 필요한 정보를 보관한다.

하지만 베타 기간에는 게임 구조가 계속 바뀌었다. 따라서 `APP_VERSION`, `CONTENT_VERSION`, `SAVE_VERSION`을 구분하고, 세이브 형식이 바뀔 때 `v1 → v2 → v3 → v4` 순서로 변환하도록 만들었다. 이전 데이터를 변환하기 전에 복구 사본을 남기며, 알 수 없는 미래 버전의 세이브를 현재 코드가 무리하게 덮어쓰지 않도록 방어한다.

저장 작업을 순서대로 처리하는 큐와, 다른 창에서 진행 데이터가 바뀌었는지 확인하는 충돌 방어도 추가했다. **브라우저에 저장한다는 사실보다, 배포를 반복해도 이미 진행한 게임이 깨지지 않게 관리하는 일이 더 어려웠다.**

### 04. PWA 업데이트와 오프라인 데이터는 같은 것이 아니다

`Workbox`의 Service Worker는 게임의 HTML·JavaScript·이미지 같은 앱 자산을 캐시한다. 반면 플레이 기록은 `IndexedDB`에 따로 보관한다. 앱 파일을 교체하는 작업과 세이브 데이터를 바꾸는 작업을 구분해야 업데이트가 안전해진다.

새 버전이 배포되더라도 플레이 중인 화면을 무조건 교체하지 않는다. `skipWaiting: false`를 유지하고, 사용자가 업데이트를 적용하는 흐름에서 저장과 호환성 처리를 수행한다. TTS로 만든 414개 음성은 최초 설치에 전부 포함하지 않고 필요할 때 받아 캐시하도록 구성했다. 따라서 **오프라인에서 사용할 수 있는 앱 자산**과 **한 번도 내려받지 않은 음성 파일**은 구분해야 한다.

또 하나 중요한 제약은 저장 데이터가 웹 주소의 **origin**에 연결된다는 점이다. 주소를 바꾸거나 Safari와 홈 화면에 설치한 PWA의 저장 영역이 다르면, 사용자가 같은 세이브를 자동으로 공유한다고 가정할 수 없다. 그래서 배포 주소를 고정하고 설치 후 플레이하는 흐름을 우선했다.

### 05. 개인 프로젝트에 맞게 선택한 복잡도의 수준

클라우드 저장, 로그인, 계정 동기화까지 처음부터 만들 수도 있었다. 대신 이 프로젝트에서는 **한 명의 사용자가 반복적으로 설치·플레이·업데이트할 수 있는 게임**에 집중했다. 그 결과 서버 비용과 운영 복잡도는 줄였지만, 기기를 바꾸거나 브라우저 데이터를 삭제했을 때 세이브가 복구된다고 보장하지는 않는다.

PWA 설치와 저장의 플랫폼 검증 절차, 자동 테스트는 마련했지만 이것만으로 모든 실제 iPhone 기기에서 Chapter 1 전체의 장시간 플레이가 검증됐다고 표현할 수는 없다. 구현된 기술적 안전장치와 사람이 직접 확인해야 하는 사용 경험은 별개로 기록했다.

**이 선택의 핵심은 앱의 모든 기능을 미리 구축하는 것이 아니라, 지금 필요한 동작은 단순하게 만들고 나중에 확장할 경계를 남기는 것이었다.**

## 단어 도움에서 학습의 흐름으로 {#learning}

Chapter 1을 만들면서 대화 도움말에 연습, 대화 기록, 노트가 더해졌다. 이어 각 장면이 표현을 소개하는지, 연습시키는지, 다시 쓰게 하는지를 콘텐츠에 표시했다. 이 작성 규칙을 동네 일상에서 오타루와 가을 축제까지 적용하면서, 표현을 여러 장면에 걸쳐 다룰 수 있게 됐다.

다음 과제는 배운 표현을 직접 쓰게 하는 것이었다. 문맥에 맞는 응답과 빈칸 채우기, 문장 조합, 게임 속 행동으로 이어지는 연습을 넣었다. 하루 끝에는 그날의 표현을 되짚는 ‘오늘의 코토바’를 추가했다. 이후에는 처음 만난 표현에 충분한 도움을 주고, 다시 등장할수록 도움을 줄여 기억에서 꺼내 쓰도록 구조를 다듬었다.

설계의 중심은 이해한 표현을 사용하고, 기억에서 꺼내 다른 상황에 다시 쓰는 흐름이다. 이 구조는 구현됐으며, 실제 학습 경험과 표현의 적절성은 일본어 학습자의 플레이테스트로 확인할 단계에 있다.

자연스러운 학습 구조를 만들면서 가장 어려웠던 부분은 "내가 일본어를 잘 모른다."였다. SW 개발자인 나는 게임 개발은 해본 적이 없어도, 기본적으로 SW를 관리하고 엔지니어링하고 배포할 방법은 잘 생각해낼 수 있다.

현실에서 "일본어 학습 게임 개발"에서 "일본어"는 실제 도메인 지식이 있는 사람의 몫이다. 기획자나 전문가가 그 역할을 맡게 된다. 하지만 그런 지식 없이 그저 개발에 도전하는 내 입장에서는 온전히 AI Agent가 가진 지식만으로 학습 과정이 적절한지, 일본어 예시는 적절한지 판단을 위탁할 수밖에 없었다.

이 과정에서 계속 느낀 생각은, '개발자는 여전히 기획자가 필요할 수 있겠지만, 기획자는 점점 개발자를 필요로 하지 않을 수 있겠다.'였다. 물론 내가 고민하고 결정했던 배포 방식이나 SW의 형태 등을 기획자가 할 수 없을 거라 생각할 수 있겠지만.. 🤨

단순 상상력으로 가능했던 스토리 기획과는 다르게 이 부분은 꽤나 어려움을 많이 겪었다. 스스로 개선하기 어렵다는 생각이 많이 들었다.

## 화면의 기준을 다시 세우다 {#visuals}

초기 아트 방향은 픽셀 그래픽이었다. 지도 크기와 이동 거리, 충돌과 화면 구도를 정리한 뒤, 상점가와 히로시의 가게를 대표 장면으로 만들었다. 하지만 이 화면은 기대한 디자인 수준에 미치지 못했다. 로드맵에는 고해상도 이미지로 교체해도 기존의 거친 픽셀 렌더링 방식을 유지한 탓에 원하는 인상이 나오지 않았다고 기록되어 있다.

다시 잡은 방향은 부드러운 일러스트풍의 2D 치비 RPG였다. 같은 상점가와 가게의 아트를 다시 만들고, 픽셀을 그대로 확대하던 렌더링도 고해상도 화면에 맞게 바꿨다. 이 대표 장면이 검토를 통과한 뒤에 Chapter 1의 지도 전반으로 확장했다.

확장 과정에서는 터치 입력과 이미지가 겹치는 순서도 손봤다. 기념품을 얻은 상태와 집에 놓은 상태를 구분하도록 저장도 수정했다. 화면 개선은 자산 교체에서 끝나지 않았고, 이동·상호작용·저장을 함께 조정하는 작업으로 이어졌다.

:::technical-details | 비주얼 재설계 과정 자세히 보기 | 픽셀 아트의 한계 → 렌더러 수정 → Golden Scene → Chapter 1 확장
### 01. 고화질 에셋을 넣었는데도 화면이 거칠었다

초기 코토마치는 포켓몬스터에서 떠올릴 법한 픽셀 기반 탑다운 RPG를 목표로 했다. 그래서 작은 논리 화면과 픽셀 단위 렌더링을 중심으로 게임이 구축됐다. 이후 더 부드럽고 아기자기한 캐릭터와 배경 이미지를 만들었지만, **원본 이미지의 해상도가 올라간다고 실제 게임 화면의 표현 방식까지 바뀌는 것은 아니었다.**

기존 렌더러는 픽셀 경계를 드러내는 확대 방식과 저해상도 스프라이트의 영향을 여전히 받고 있었다. 새로 그린 캐릭터도 게임 안에서는 각지고 거칠게 보였고, 치비 캐릭터의 머리와 몸 비율도 레퍼런스 이미지의 인상과 달랐다. M4-B에서는 기술적 동작 검증을 통과한 결과물조차 **실제 디자인 검토에서 거절**됐다. 코드가 작동한다는 것과 원하는 미적 품질을 달성했다는 것이 다르다는 사례였다.

### 02. 이미 고친 월드 구조를 버리지는 않았다

앞선 M4-A 작업은 실패한 것이 아니었다. 상점가의 빈 공간을 줄이고, 히로시의 가게에 선반과 계산대 등을 집중시키며, 카메라 구도와 이동 거리, 오브젝트 밀도, 충돌, 깊이 정렬(`sortY`)을 정리한 성과가 있었다. 문제는 맵 구조가 아니라 **그 구조를 보여주는 시각적 언어**였다.

따라서 Agent는 M4-A에서 정리한 이동·공간 구조를 유지한 채, M4-B의 아트 기준을 폐기하고 M4-R을 새 기준으로 삼았다. 2D 탑다운이라는 게임 방식은 남겨 두되, 굵은 픽셀 표현 대신 **부드러운 일러스트풍의 2등신 안팎 치비 캐릭터**를 제작 기준으로 확정했다.

### 03. 논리 좌표와 실제 그리는 해상도를 분리하다

기술적으로 가장 중요한 전환은 게임의 좌표계와 그림의 해상도를 분리한 일이었다. 기존의 `480 × 270` 논리 뷰포트는 카메라, 캐릭터 이동, 맵과 이벤트 위치를 계산하는 데 계속 활용할 수 있다. 하지만 이 숫자가 그림의 최대 해상도를 결정할 필요는 없었다.

새 렌더링 방향은 `게임 논리 좌표 → 카메라 변환 → DPR을 반영한 Canvas 해상도 → 고해상도 아트의 부드러운 축소 렌더링`이다. `nearest-neighbor`식의 거친 확대를 고집하지 않고, 이미지 스무딩과 고해상도 원본 에셋을 사용해 최신 휴대폰에서도 윤곽이 자연스럽게 보이도록 했다.

서연과 주요 NPC에게는 네 방향의 표정·자세와 여러 프레임의 걷기 동작을 적용했다. 발이 바닥에 닿는 기준점이 흔들리지 않도록 하고, 단순히 그림을 옆으로 밀기보다는 다리의 움직임과 체중 이동이 드러나도록 조정했다. 고해상도 에셋을 써도 **캐릭터의 충돌 영역과 이벤트 위치는 그림 파일 크기에 종속되지 않아야** 했다.

### 04. 캐릭터가 서 있는 위치가 그림의 앞뒤를 결정했다

상점가와 가게 내부는 배경을 예쁘게 그리는 것만으로 완성되지 않았다. 캐릭터가 선반 뒤로 지나가면 일부가 가려져야 하고, 가게의 지붕이나 차양은 플레이어보다 앞에 표시될 수도 있다. 이 과정에서 `sortY`, 발 위치 기준 정렬, 전경(상부) 레이어, 카메라, 충돌 판정을 함께 보완했다.

모바일에서는 조이스틱 조작으로 오브젝트 가까이 다가갈 수 있으므로, **보이는 장애물의 형태와 실제 이동 가능한 공간이 일치하는지**가 중요했다. NPC가 자연스럽게 바라보는 방향과 작은 대기 동작도 게임 화면의 인상에 영향을 줬다. 시각적 폴리싱처럼 보이지만 입력·이동·충돌·상호작용이 연동된 개발이었다.

### 05. 한 장면을 기준으로 만들고 전체 맵에 적용했다

처음부터 모든 지역의 이미지를 한꺼번에 교체하지 않았다. 먼저 **다누키코지 상점가와 히로시의 가게**를 Golden Scene으로 선정했다. 서연과 히로시의 비율, 배경의 밀도, 소품의 그림체, 카메라 구도, 실제 게임에서의 선명도를 같은 장소에서 검토한 것이다. 이 대표 장면은 M4-R의 제작 기준으로 승인됐다.

이후 M5에서 삿포로의 거리·실내 공간, 오타루 운하와 가게, 가을 축제 등의 **Chapter 1 맵 계열 18개**로 같은 기준을 확장했다. 이때 맵·이벤트·학습·진행 상태의 기존 식별자는 최대한 유지해 시각적 변경이 스토리 진행을 깨뜨리지 않도록 했다.

여기서 승인된 것은 우선 **대표 장면의 방향성**이다. Chapter 1 전체는 구현과 내부 검증을 거쳤지만, 전체 플레이를 통한 최종 시각적 품질 승인과는 구분해 기록했다.

**비주얼 개발에서 배운 것은 좋은 이미지를 만드는 일보다, 그 이미지를 게임 월드에 맞게 그려 내고 움직이게 하는 일이 더 복잡할 수 있다는 점이었다.** Agent는 렌더링과 충돌 같은 구조적 문제를 해결할 수 있었지만, 최종적으로 ‘이 화면이 내가 원하던 분위기인가’라는 판단은 사람의 몫이었다.

## 만들었다고 끝나지 않는 것들 {#iteration}

대표 장면이 검토를 통과했다고 챕터 전체의 화면까지 검증된 것은 아니었다. 확장 뒤에는 대사의 화자 표시와 기념품 상태를 다시 수정했다. 학습 구조도 구현 이후 플레이테스트를 남겨 두었다. 문서에서 ‘구현 완료’와 ‘개발자의 검토 완료’를 구분하는 이유다.

Playwright 테스트와 여러 화면 크기의 캡처로 동작을 반복 점검했다. 실제 iPhone에서 확인할 PWA 검증 절차도 마련했다. 자동화로 확인할 수 있는 것은 화면과 저장 등의 동작이다. 터치감과 음성 품질, 학습의 흐름은 직접 플레이하며 확인해야 한다.

개발 기록에는 챕터 전체의 시각 검토와 학습 플레이테스트가 후속 확인 과제로 남아 있다. 아래 개발자 노트에는 실제 구현 과정에서 겪은 조작·비주얼 문제와 개선 경험을 담았다.

최근 대대적인 Visual Polish와 학습 루프 재구성을 하고 나서는, 그래도 맨 처음 기대했던 수준으로 어느 정도는 개발된 듯하다.

## Agent와 일하는 방식도 바뀌었다 {#agents}

Agent 운영 규칙도 개발 중에 바뀌었다. 9월 27일의 첫 가이드는 큰 구현을 Astra가 맡고, Sol이 독립 검토를 하며, Luna가 Git 등 가벼운 작업을 처리하도록 나눴다. 강한 모델의 구현과 별도 검토를 중심에 둔 구성이었다.

9월 29일에는 범위가 명확한 일을 Luna가 우선 맡도록 바꿨다. 모든 작업에 별도 검토를 붙이기보다, 막히거나 불확실할 때 Sol이나 Astra로 넘기는 규칙이었다. 다음 날에는 Sol이 목표 파악과 작업 분해, 통합·최종 판단을 총괄하도록 했다. Luna는 대부분의 조사와 구현을 수행하고, Astra는 Sol의 분석으로도 풀리지 않는 구조적 문제나 고위험 판단에만 호출하도록 했다.

이 역할 분담은 `.codex/config.toml`에도 반영됐다. 작업의 범위와 난도에 맞춰 모델을 쓰고, 전체 작업량을 줄이려는 변화다. 다만 이 기록은 운영 규칙의 변화이지, 과거 모든 커밋을 어떤 Agent가 만들었는지에 대한 증거는 아니다.

:::technical-details | Agent 하네스 설계 자세히 보기 | Astra 중심 → Luna-first → Sol 오케스트레이션 · 검증과 위임 규칙
### 01. 처음에는 강한 모델과 별도 검수를 중심에 뒀다

초기의 Agent 운영은 큰 구현을 **Astra**에 맡기고, **Sol**이 별도로 검토하며, **Luna**가 Git 작업 등 비교적 가벼운 일을 수행하는 형태였다. 강한 모델이 많은 것을 처리하고 그 결과를 다른 모델이 확인하면 안정적일 것이라는 접근이었다.

그러나 코토마치처럼 지도·대사·학습·저장·이미지·오디오를 연속적으로 고치는 프로젝트에서는 작은 수정도 자주 발생한다. 매번 가장 무거운 모델을 쓰거나 모든 작업에 별도 검수를 붙이면 구현 범위보다 조정·검토에 쓰는 자원이 커질 수 있었다. 토큰 사용에 대한 실제 경험과 고민은 이 펼치기 뒤에 이어지는 개발자 노트에서 직접 이야기한다.

### 02. Luna-first에서 Sol 오케스트레이션으로

9월 29일에는 **Luna가 범위가 명확한 작업을 우선 처리하는 Luna-first** 원칙으로 전환했다. 일반 기능 개발이나 디버깅은 Luna가 직접 구현·테스트까지 진행할 수 있게 하고, 막힐 때만 상위 모델의 추론을 활용하는 방식이었다.

9월 30일에는 이를 한 단계 더 정리해 **Sol이 전체 작업을 지휘하는 오케스트레이터**, **Luna가 주 구현 워커**, **Astra가 중요한 구조적 판단을 위한 최종 에스컬레이션** 역할을 맡도록 했다. 단순히 모델 이름을 바꾼 것이 아니라, 누가 요구사항을 분해하고 어떤 조건에서 검수를 추가하는지까지 규칙으로 만들었다.

### 03. 실제 설정 파일에 남은 운영 정책

역할 분담은 말로만 정하지 않고 저장소의 `.codex/config.toml`과 `AGENTS.md`에 반영했다. 최종 설정에는 `model = "gpt-6.1-sol"`, `model_reasoning_effort = "medium"`이 들어 있고, 기본 서브에이전트는 `gpt-6-luna`의 `high` 추론으로 지정되어 있다. 한 세션의 동시 에이전트 작업 수는 최대 `2`로 제한했다.

`AGENTS.md`에는 모델별 역할뿐 아니라 문서를 읽는 범위, 독립 작업을 나누는 기준, 테스트의 깊이, Git 반영 절차가 함께 적혀 있다. 예를 들어 **서로 같은 파일을 동시에 수정하는 병렬 작업은 피하고**, 경계가 분명한 별도 작업만 나누도록 했다. 무조건 많은 Agent를 투입하는 것이 목표가 아니었다.

### 04. 한 번의 개발 요청이 흘러가는 방식

기본 흐름은 `사용자 요구 → Sol의 범위·완료 조건 정의 → Luna의 코드·문서 탐색과 구현 → 관련 테스트 → Sol의 통합 판단 → Git 반영`이다. 구현 중 설계 충돌이 생기거나 위험도가 높으면 Sol이 다시 분석하고, 필요할 때만 Astra까지 올린다.

작은 변경은 담당 워커가 검증까지 마치고 종료할 수 있고, **모든 수정에 두 번째 Agent의 형식적인 검수를 의무화하지 않는다.** 반대로 세이브 호환성, 업데이트, 기존 진행 데이터 같은 위험한 변경은 더 넓은 회귀 검증이 필요하다. 베타 기간에는 완성된 작은 기능을 자주 `main`에 반영해 배포된 게임에서 직접 확인하는 흐름도 중요했다.

문서를 관리하는 방식도 이와 연결된다. `AGENTS.md`는 Agent가 어떻게 일할지 정하고, 자세한 게임 기획·UI·음성·저장 기술의 기준은 `docs/`에 분리했다. 장기 프로젝트에서 한 번 확정한 설계를 Agent가 임의로 뒤집지 않도록 하는 장치였다.

### 05. 효과를 기록할 때 구분해야 할 것

이 방식은 **모든 작업에 최고 추론 모델을 쓰는 대신, 작업 난도에 맞춰 추론과 검증 비용을 배분하자**는 운영 전략이었다. 특히 코드 생성보다 실제 테스트, 결과 비교, 오류 수정, Git 정리까지 이어지는 과정에서 하네스 규칙의 가치가 드러났다.

다만 저장소에서 확실히 확인할 수 있는 것은 **어떤 설정과 운영 정책이 도입됐는가**이다. 모든 과거 커밋을 어떤 모델이 작성했는지, 전체 개발 시간이 몇 퍼센트 단축됐는지까지 이 기록만으로 입증할 수는 없다. 토큰 소비 변화와 체감 효율에 대한 평가는 개발자가 직접 작성한 노트에 남겨 두었다.

**코토마치의 하네스는 거대한 멀티 에이전트 시스템을 만드는 실험이 아니었다.** 다양한 난도의 일을 적절한 모델에 맡기고, 사람이 확인해야 할 결정은 남겨 두면서, 한 프로젝트를 지속적으로 완성해 가기 위한 작업 방식이었다.

## 목소리까지 입히고 Chapter 1을 마치다 {#open-work}

음성은 Chapter 1에서 마지막까지 남아 있던 제작 과제였다. 첫 시제품에서는 미리 생성한 음성 파일을 사용했고, PWA 전환 이후에는 브라우저의 Web Speech로 일본어 대사를 읽도록 바꿨다. 그러나 기기에 따라 사용할 수 있는 일본어 음성과 음색이 달랐고, 등장인물별로 일관된 목소리를 만드는 데에는 한계가 있었다.

10월 7일, 한동안 보류했던 음성 작업을 다시 진행했다. AivisSpeech의 CPU 기반 합성 방식을 검증하고, 실제 샘플을 들어본 뒤 캐릭터별 음성 설정을 확정했다. 서연·사치코·히로시·아야카와 일반 NPC의 목소리를 배정하고, 합성한 결과를 압축된 MP3 파일로 제작했다. 게임을 실행할 때마다 음성을 생성하는 대신, 제작 단계에서 만든 파일을 재생하는 방식이다.

제작 범위는 Chapter 1의 실제 발화 대상 대사를 기준으로 잡았다. 고정 대사뿐 아니라 플레이 중 선택하거나 구성한 문장의 발화도 포함하고, 화면 안내문처럼 원래 읽지 않는 텍스트는 제외했다. 그 결과 **대상 일본어 발화 414개 중 414개(100%)**의 음성 제작과 자동 검증을 완료했다. 음성 파일은 약 11.5MiB 규모로, 다섯 차례에 나눠 제작하고 GitHub와 Vercel 배포까지 마쳤다.

게임에서는 준비된 캐릭터 음성을 우선 재생하고, 파일을 불러오지 못할 때는 기존 Web Speech를 대체 수단으로 사용한다. 모든 음성을 설치 시 한꺼번에 내려받지 않고 필요할 때 불러오도록 구성했다. 자동화 테스트와 배포 파일 확인은 통과했지만, 모든 대사의 사람 귀로 듣는 발음 검수와 실제 iPhone에서의 장시간 플레이 검증은 별개의 후속 확인 항목으로 남아 있다.

:::technical-details
### 01. 기기에서 빌려 온 목소리의 한계

첫 시제품에는 미리 만든 일본어 음성 파일 일곱 개가 있었지만, PWA로 전환한 뒤에는 브라우저의 `Web Speech API`를 기본 방식으로 삼았다. 게임이 일본어 문장을 전달하면 아이폰이나 MacBook에 설치된 일본어 음성으로 읽어 주는 구조였다. 서버도 별도의 API 비용도 필요하지 않다는 장점이 있었다.

Agent는 캐릭터 이름에 따라 음성 프로필을 선택하도록 만들고, 말하는 속도(`rate`), 높낮이(`pitch`), 가능한 음성 목록에서의 선택 순서까지 조정했다. 그럼에도 아이폰에서는 여성 캐릭터들의 목소리가 비슷하게 들렸고, MacBook에서는 또 다른 음색이 나왔다. 사용 가능한 일본어 목소리 자체가 운영체제와 기기에 달려 있었기 때문이다. **게임이 등장인물의 목소리를 직접 통제하지 못한다**는 것이 가장 큰 제약이었다.

### 02. 자연스러운 일본어 음성을 위한 오픈소스 탐색

다음 방향은 실행할 때마다 음성을 요청하는 유료 API 대신, 개발 과정에서 음성을 미리 제작할 수 있는 오픈소스 TTS였다. Agent는 일본어 음성 합성 엔진인 **AivisSpeech**와 **VOICEVOX**를 조사하고, 실제 합성 가능성뿐 아니라 모델별 음색, 라이선스, 실행 자원도 검토했다.

최종적으로 검증한 엔진은 `AivisSpeech Engine 1.2.0`이었다. 일본어 합성에는 **Style-Bert-VITS2 JP-Extra** 기반의 공개 음성 모델을 사용했다. VOICEVOX 역시 후보였지만, 이번 작업에서 실제 설치·속도 비교까지 진행한 것은 아니다. 엔진의 오픈소스 라이선스와 개별 음성 모델의 사용 조건은 별도로 확인했다. 게임에 배포할 것은 모델 자체가 아니라 **합성한 음성 파일**이기 때문이다.

### 03. MacBook에서 잠시 멈춘 이유

당시 코토마치의 주된 개발 환경은 개인 MacBook이었다. 로컬에서 Docker 등을 사용해 TTS 엔진과 모델을 구동하는 방안을 고려했지만, 모델 파일과 추론에 필요한 메모리·CPU 자원까지 관리하면서 게임 개발을 병행하기에는 부담이 컸다. 그래서 비주얼과 학습 콘텐츠를 우선 완성하고 음성 제작은 뒤로 미뤘다.

당시에는 MacBook에서 정식 성능 시험을 진행하기보다, **로컬 자원 부담을 고려해 다른 개발 작업을 우선했다.** 아래 개발자 노트에 남긴 ‘컴퓨터 리소스로 인해 잠시 미뤘다’는 말도 그 시점의 판단을 보여준다.

### 04. Codex Cloud에서 음성 합성을 실행하다

10월 7일 다시 시작한 작업의 전환점은 **Codex Cloud에서 엔진을 직접 구동한 것**이었다. Agent는 Linux 환경에 AivisSpeech를 설치하고, 공개 모델을 내려받아 HTTP API로 일본어 문장 합성을 시험했다. 실제 환경은 **2 CPU 상당의 할당량, 메모리 제한 8 GiB, GPU 없음**이었다.

엔진의 `/audio_query`에서 텍스트의 발음·합성 설정을 준비하고, `/synthesis`에 모델의 화자/스타일 ID와 파라미터를 전달해 WAV를 얻었다. 일본어 한 문장을 실제로 합성하는 POC에 성공한 뒤, 게임 대사로 오디션 샘플을 제작했다. **로컬 장비에 모델을 계속 띄워 두지 않고도 CPU만으로 제작이 가능하다**는 사실이 확인된 것이다.

음성을 듣고 배역을 확정한 뒤에는 서연과 사치코에 `morioki`, 히로시에 `阿井田 茂`, 아야카에 `まお` 모델을 배정했다. 서연과 사치코는 같은 기본 모델이지만 사치코 쪽 속도를 `0.84`, 피치를 `-0.12`로 조정했다. 실제 노년 여성의 별도 학습 모델을 만든 것은 아니다. 다른 일반 NPC도 세 모델을 바탕으로 각자의 고정 음성 프로필을 갖도록 했다.

### 05. 414개의 대사를 게임에 연결하는 파이프라인

엔진을 실행하는 데 성공했다고 곧바로 게임에 적용할 수 있는 것은 아니었다. 코토마치는 고정 대사뿐 아니라 **플레이어의 선택이나 문장 조합 결과도 일본어로 발화**하기 때문이다. Agent는 Chapter 1의 77개 이벤트에서 실제로 재생될 수 있는 문장을 추출했다. 화면에만 표시되는 안내·독백 등을 제외하고 남은 대상은 **414개**였다.

제작 흐름은 `대사 추출 → 캐릭터/모델 매핑 → AivisSpeech 합성 → FFmpeg MP3 변환 → 검증 → GitHub/Vercel 배포`였다. 출력은 모노 24 kHz·64 kbps MP3로 통일하고, 음량 정규화도 적용했다. 단순히 파일을 반복 생성하는 대신 원문, 모델 버전, 합성 파라미터, 발음 사전, 인코딩 설정 등을 조합한 **SHA-256 Fingerprint**로 파일을 관리했다. 문장이 그대로라면 기존 파일을 재사용하고, 달라진 음성만 다시 생성하도록 만든 것이다.

실제 오류도 수정했다. `小樽`를 잘못 읽는 문제는 사용자 발음 사전에서 `オタル`로 고쳤고, `幸子`를 엉뚱하게 읽는 경우에는 TTS 입력만 `サチコ`로 교정했다. 게임 화면의 원문과 대사 ID는 건드리지 않았다. 작업이 중간에 끊기면 완료된 음성을 임시 기록에서 복구하는 **이어 만들기(staging/resume)** 기능도 추가했다.

최종적으로 5번의 배치 작업에서 **414개 음성 전부를 생성**했고, MP3 합계는 **11.48 MiB**였다. 생성된 음성은 게임 실행 중 필요한 순간에만 내려받아 재생하고, 실패하면 기존 `Web Speech API`로 돌아간다. PWA는 최근 들은 파일을 캐시하며, 설치 시 414개를 한꺼번에 다운로드하지 않는다.

자동 검사에서는 414개 파일의 생성·디코딩과 배포 파일의 크기·해시가 일치했고, 최종 브라우저 통합 테스트도 **34/34 통과**했다. 다만 **일본어 발음과 연기의 사람 귀로 듣는 검수, 실제 아이폰의 장시간 재생 검증은 이 수치와 별개**로 남겨 두었다.

## 개발자 인터뷰 {#interview}

아래 질문은 KotoMachi를 만들며 겪은 기획과 개발, 그리고 AI Agent와의 협업 경험을 돌아보기 위해 정리했다. 답변은 heeyoon이 직접 작성했다.

### 처음 KotoMachi를 만들려고 했을 때, 어떤 걸 만들어보고 싶었나요?

:::human-answer
처음에는 대놓고 공부하는 앱을 만들고 싶진 않았습니다. 제가 좋아했던 게임의 환경을 상상하며, 재미있는 게임을 하면서 자연스럽게 언어를 배우는... (실제로 저는 그런 게임은 안 해봤습니다.) 그런 게임을 상상했었습니다.

다만 그러다 보니 실제로 기획하는 단계에서는 '학습'보다는 '디자인'에 훨씬 신경을 많이 쓰게 되었던 것 같습니다. 제 입맛대로 만들어진 아기자기한 세상을 보고 싶다는 느낌?
:::

### 시작할 때 AI Agent가 어느 정도까지 해줄 거라고 기대했나요?

:::human-answer
개발을 시작하기 일주일 전에 Astra가 출시되었습니다. AGI의 등장이라길래 기획 단계에서도 Astra에게 좀 자율성을 부여하고 시키면 흔히 말하는 '딸깍' 게임 개발이 가능할까 싶었지만... 토큰만 불타는 결과가 나오기는 했죠.

아무리 똑똑한 모델이어도 워낙 만들려는 게임의 형태가 모호했을까 싶다가도, 그렇게 설계 문서와 레퍼런스 디자인을 많이 줬는데도 이 정도야? 싶은 생각은 정말 많이 들었습니다.
:::

### 실제로 개발해보니 그 기대와 가장 달랐던 점은 무엇이었나요?

:::human-answer
‘게임’ 개발을 가볍게 처음 해봐서 그런지 모르겠지만, 디자인 수준을 올리는 과정이 생각보다 되게 어렵다는 느낌을 받았습니다. 생성부터 자연스러운 동작까지 다 알아서 잘 해줄 듯했는데, 막상 사소한 버그 픽스 과정도 정말 많았습니다.

안 좋은 이야기만 하는 것처럼 보이겠지만, 사실 이런 개발을 혼자 해야 한다면 시작도 안 했을 겁니다. 이렇게 원하는 대로 제품을 만드는 것 자체가 재미있는 경험인 것도 맞아서, 과정 자체는 아주 즐거웠습니다.
:::

### 만들면서 가장 크게 방향을 바꾼 결정은 무엇이었나요?

:::human-answer
학습 루프와 비주얼, 두 가지입니다. 비주얼이야 앞서 말한 대로 눈에 보이는 게 마음에 안 들어서 직접 고치려 했다면, 학습 루프의 경우 기획 단계에서 생각했던 이 앱의 역할을 크게 바꾸는 결정이었습니다.

이 앱의 유일한 사용자가 기대하는 학습 요소와는 전혀 다른 형태로, 단순히 제가 생각했을 때 이렇게 하면 되겠지?라는 느낌으로 초기 기획을 했고, 그 외에는 스토리 기획에만 집중하다 보니 그냥 ‘일본어 스토리 게임 앱’이 되어버렸습니다.

단순히 혼자서 만들었다면 큰 수정은 없었겠지만, 역시 앱이나 서비스는 사용자가 있을 때 더 빠르게 발전할 수 있다는 생각도 들었습니다.
:::

### Agent에게 일을 맡길 때 가장 중요하다고 느낀 것은 무엇이었나요?

:::human-answer
‘목적이 무엇인가’가 가장 중요하다고 느껴집니다. 결국 내가 명확한 비전을 제시하지 못하면, AI Agent도 그만큼 명확하게 결과물을 만들기는 확실히 힘들어 보입니다.

그리고 귀찮지만, 여러 내용을 명확하게 문서화하고 관리하는 일은 긴 호흡의 개발 과정에서 AI Agent가 길을 잃지 않도록 도와주는 느낌도 확실히 듭니다.

물론 이런 것들도 Agent 모델이 더 크고 똑똑해지고, 기본 하네스 구조가 방대해지면 더 이상 사람이 신경 쓸 게 하나도 없을 듯하다고 느낍니다.
:::

### 좋은 모델 하나를 쓰는 것과 역할을 나누고 하네스를 만드는 것 중, 무엇이 더 중요하다고 느꼈나요?

:::human-answer
사실.. 비용 및 토큰에 대한 고민이 없다면 당연히 좋은 모델 하나로도 괜찮지 않을까 싶습니다. 단순 작업에 무거운 추론이 필요 없다는 건 속도와 비용 측면에서의 시선이라고 생각합니다.

무엇이 중요하냐?라는 질문에 어느 하나를 고르기는 좀 어렵긴 하네요. 하지만 굳이 따지자면, 역할을 나누고 하네스를 만드는 것에도 결국 오케스트레이션을 해줄 좋은 모델이 필요하지 않을까라는 생각이 듭니다.
:::

### Agent와 개발하면서 가장 답답했던 순간은 언제였나요?

:::human-answer
초반 기획 단계에서 강하게 잡힌 콘셉트를 뒤엎는 데까지 시간과 노력이 많이 쓰인 것 같습니다. 기획 단계에서 생각했듯이 ‘포켓몬스터’ 같은 픽셀 기반 게임 화면을 초기 콘셉트로 잡다 보니, 이후의 디자인도 계속 그 기반으로 만들어져서 답답한 과정이 좀 있었습니다.
:::

### 반대로 “이건 생각보다 정말 잘한다”고 느낀 순간은 언제였나요?

:::human-answer
정말 잘한다는 게... 뭐 한두 개가 아니긴 합니다, 사실. 가장 신기했던 부분은 코드 생성보다 검증하는 방식들이었습니다.

웹 브라우저를 실제로 열어서 하나하나 확인해보고, 개발한 결과에서 버그가 발견되면 그 내용까지 확인해서 다시 수정한 뒤 검수하고, 음성 기능 같은 경우도 직접 재생시켜가면서 확인하는 그 과정이 약간 소름 돋기도 했습니다. (밤에 자꾸 음성 테스트를 해서 맥북 소리를 껐습니다.)

사실 아무리 웹앱이라고 해도 이런 게임 형식의 시스템을 만들 수 있다는 것 자체가 대단하다고 느껴집니다. 더해서 기획 단계에서도 GPT와 편하게 대화하면서 구체화해가는 과정이 정말 좋다고 느꼈습니다.
:::

### 직접 대부분의 코드를 작성하지 않았는데도, KotoMachi를 ‘내가 만든 프로젝트’라고 느끼나요?

:::human-answer
주변 사람들, 특히 AI Agent에 관심이 크게 없는 분들은 전부 당연히 제가 만들었다고 이야기해줍니다. 생각해보면 기획부터 디자인, 전체 스토리 등 제가 생각하지 않은 부분은 하나도 없지만, 말 그대로 “제가 직접 만든 부분”은 전혀 없습니다.

사실 이런 식으로 이야기하면 추상화 수준을 논하면서, 원래 파이썬이나 자바도 고수준 언어이기 때문에 실제로 만들었다고 할 수 없다~라고 하면 또 그 의견이 맞는 것 같다가도, 어쨌든 코드 파일의 모음이라는 블록으로 쌓기를 하던 작업에서 이제는 블록이 알아서 쌓이고, 쌓인 결과를 중간중간 확인하는 사람이 되었기에 “감독”은 했으나 “제작”을 했다고 하기는 어렵나? 싶은 생각이 듭니다.

말하고 보니 건물 설계자도 직접 벽돌을 나르지는 않지만 분명히 그 건물을 만드는 데 큰 역할을 하네요? 이제 벽돌을 직접 올리는 ‘개발자’보다 ‘SW 설계자’라는 말이 더 어울리겠습니다.
:::

### 다음 프로젝트를 다시 Agent와 만든다면 처음부터 무엇을 다르게 하고 싶나요?

:::human-answer
일단 디자인적인 측면에서 훨씬 강하게 초반 설계와 레퍼런스 이미지를 만들 것 같습니다. 사실 이미지 몇 개만 가지고는 전체 게임을 만드는 게 불가능하다는 것을 몸소 느꼈습니다. 아무래도 게임인 만큼 디자인이 확 끌려야 또 할 맛이 나죠.

중간에 바꾼 하네스 정책도 처음부터 적용하고 싶습니다. 그랬다면 훨씬 더 빠른 개발을... 했을지도..

물론 이런 시행착오가 있기에 경험으로서 더 의미가 있다고 생각합니다.
:::
