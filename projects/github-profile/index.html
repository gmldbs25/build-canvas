01 / WHY

프로필은 이력서보다
작은 쇼윈도에 가깝다.

GitHub에는 내가 작성한 코드가 쌓이지만, 처음 방문한 사람은 저장소 이름만 보고 그 안에서 무슨 일이 벌어지는지 알기 어렵다. 그래서 기술 목록보다 완성된 결과물을 먼저 보여주기로 했다. 프로필 README는 짧게, 자세한 제작 과정은 Build Canvas로 연결하는 방식이다.

BEFORE

간단한 자기소개와 저장소 목록. 프로젝트를 직접 실행해 보기까지 여러 번의 클릭이 필요했다.

AFTER

실제 게임 화면과 시뮬레이터 화면, 실행 링크, 개발 기록으로 이어지는 명확한 진입점.

02 / SHOW THE WORK

설명보다 먼저,
실제로 동작하는 화면.

Private 저장소를 공개하지 않고도, 배포된 제품의 화면과 실행 링크는 공개할 수 있다. 대표 이미지는 생성한 일러스트가 아니라 Vercel에 배포된 앱을 직접 캡처했다.

04 / HOW IT WORKS

README 하나 뒤에
작은 자동화 두 개.

IMPLEMENTATION

프로필은 별도의 웹사이트가 아니다. 사용자명과 같은 공개 저장소의 README가 GitHub 메인에 표시된다. 이미지는 정적 파일로, 3D 그래프는 SVG로 연결한다.

앱의 실제 캡처는 Playwright가 Vercel 배포 화면을 열어 WebP로 저장한다. 기여 그래프는 GitHub Actions가 생성하고 매일 갱신한다.

gmldbs25 / gmldbs25 · public
README.md
  ├─ Featured Projects
  │   ├─ assets/kotomachi.webp
  │   └─ assets/fabflow.webp
  │       ↳ Playwright captures
  │         deployed Vercel apps
  └─ 3D Contributions
      └─ profile-3d-contrib/*.svg
          ↳ scheduled GitHub Actions

Output → github.com/gmldbs25
01 / COMPOSITION

작게 소개하기

텍스트 위주의 프로필을 프로젝트 카드, 배포 링크, Build Canvas 링크로 정리했다. 버전 번호와 방문자 수 같은 시시각각 바뀌는 정보는 제외했다.

02 / CAPTURE

실화면을 자산으로

Playwright가 실제 앱을 실행하고 대표 장면을 캡처한다. KotoMachi는 인게임 화면보다 타이틀 화면이 첫인상에 더 적합했다.

03 / AUTOMATION

유지보수 줄이기

3D 그래프는 Actions로 생성하며 한국시간 오전 3시에 갱신하도록 설정했다. README가 참조하는 이미지 URL의 캐시 버전도 함께 변경한다.

05 / LEARNED

완성보다 까다로웠던
작은 디테일.

기여 숫자가 달랐다.

처음 생성한 3D 그래프와 GitHub 기본 잔디의 기록이 맞지 않았다. 원인은 비공개 기여의 공개 표시 설정. 수치뿐 아니라 데이터 범위와 접근 권한을 함께 확인해야 했다.

갱신돼도 옛 이미지가 보였다.

SVG 파일은 바뀌었지만 같은 주소를 참조하면서 이미지 캐시가 남을 수 있었다. 자동 생성 시 URL에 버전 값을 붙이도록 조정했다.

자동화끼리도 충돌했다.

스크린샷과 기여 그래프 작업이 같은 프로필 저장소를 업데이트하면서 push 충돌이 발생했다. 최신 main을 확인한 뒤 재시도하는 방식으로 개선했다.

RESULT

GitHub는 시작점.
이야기는 Build Canvas에서.

프로필에는 무엇을 만들었는지만 남긴다. 왜 만들었고 어떻게 고쳤는지는 이곳에 기록한다. 역할이 분명해지니 두 공간 모두 더 간결해졌다.
