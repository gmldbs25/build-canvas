## 1. 작품의 정체성
**공개 제목:** Behind the Simulation  
**한 줄:** 움직이는 공장 뒤에는 어떤 규칙이 있을까?  
**성격:** FAB FLOW의 실제 3D 세계를 활용해 모델링·시간·경로·혼잡·검증·렌더링을 발견해 나가는 인터랙티브 엔지니어링 아티클.

### 관람 대상·경험
- 반도체 전공이 없는 개발자와 기술에 관심 있는 일반인도 기본 서사를 이해할 수 있어야 한다.
- 화면만 따라가도 전체 이야기를 파악하고, 원하면 **조금 더 깊게**에서 실제 구현에 접근한다.
- 본편 목표 분량은 약 6~8분 **설계상 예상치**(사용자 검증 전 실측치가 아님). 본문은 압축하고 심화는 선택사항.
- 목적은 FAB FLOW의 3D 세계를 **다시 체험시키는 것**이 아니라, 그 뒤의 설계와 엔지니어링 판단을 이해시키는 것.
- 이미 완성된 FAB FLOW의 Introduction/Experience를 Work6에서 4장면에 걸쳐 반복하지 않는다.
- 미래 AI/FLOW INTELLIGENCE를 현재 구현된 기능처럼 소개하지 않는다. 이 리워크는 이미 구현·검증된 시뮬레이션 기술 중심.

## 2. 절대 원칙
1. **Native visual first:** 이미 Work6에 들어온 원본 FAB FLOW Three.js 모델·레일·OHT·FOUP·카메라·운송 상태·색상·재질을 1순위로 쓴다. 새 공장·차량·FOUP 그림/메시/가짜 이동 루프 제작 금지.
2. **Narrative owns explanation, Engine owns truth:** Work6는 질문, 텍스트, 시점, 주석, 선택 인터랙션을 소유한다. 숫자와 물리·경로·운송 상태는 실제 엔진 또는 명시적으로 출처가 있는 검증 보고서에서 가져온다.
3. **One scene, one idea:** 장면당 전달할 문장 하나, 주요 시각 현상 하나, 필요할 때만 주요 조작 하나. 별도 버튼을 누르지 않아도 기본 서사를 이해할 수 있어야 한다.
4. **Show → Notice → Explain:** 장면 시작은 3D 현상/실제 결과를 보여주고, 짧은 질문을 제시한 후, 해설하고, 기술 심화는 접어둔다.
5. **정확한 구분:** 실제 움직임 / 실측 KPI / 기술 설명용 개념을 시각적으로 구분. 대안 경로는 실제 선택된 경로가 아닐 수 있으며, wait는 deadlock과 같지 않다.
6. **기존 FAB FLOW 불변:** 원본 gmldbs25/fab_flow 수정·배포 금지. Build Canvas Work1~5와 홈 링크·키보드 공통 규칙 유지.
7. **낯익은 세계:** FAB FLOW의 따뜻한 아이보리·민트·앰버 3D 외관 그대로. Work6의 개성은 콘텐츠 편집, 프레이밍, 집중 강조, 텍스트 리듬에서 나온다.

## 4. 장면별 콘텐츠·연출 계약
모든 장면은 **제목 1줄 + 본문 1~2문장 + 3D 주인공 + 필요한 순간의 하나의 주요 컨트롤**을 기본으로 한다.

### Scene 01 — 작은 공장이 움직인다
- 화면: 원본 Large V6 FAB의 근사 전체 뷰. 실제 여러 OHT가 운행 중이다. 선택된 한 대에 자연스럽게 시점/강조가 모인다. 전체 3D를 가리는 카드·대형 글자는 피한다.
- 제목: **이 작은 공장은 어떻게 움직일까?**
- 본문: **화면 속 차량은 정해진 영상을 반복하지 않습니다. 어느 길로 가고, 언제 멈추는지 시뮬레이션이 결정합니다.**
- 시퀀스: 전체를 1~2초 관찰 → 실제 한 OHT 포커스(자동, 스킵 가능) → 장면 이동. 임의 신규 3D나 재생 영상 불가.
- 심화: 없음. 시작부터 전문용어 7개를 설명하지 않는다.

### Scene 02 — 공장을 그래프로 바꾸면
- 화면: **같은 FAB FLOW 레일**을 두 관점으로 보여준다. 기본 장비/레일 뷰 ↔ 실제 방향성 레일/선택 링크 강조. Node·Link·Port는 기존 3D 상의 실제 객체/경로에 라벨만 부착한다.
- 제목: **공장 안의 길은 어떻게 코드가 될까?**
- 본문: **화면에서는 레일이지만, 엔진은 연결된 지점과 이동할 수 있는 방향으로 이 공장을 이해합니다.**
- 컨트롤: **공장 보기 / 길찾기 구조 보기** 한 개. 시각 효과는 기존 원본 레일·네트워크 표현의 상태 전환이지 별도 가짜 그래프 애니메이션이 아니다.
- 선택 심화: Directed Graph, Node·Link·Port, 모델링에서 남긴 것과 생략한 것.

### Scene 03 — 운송 한 건의 일생
- 화면: 원본 TutorialCommandLayer/Engine + Native ThreeFacilityScene의 실제 차량/FOUP/Port; 근접 Follow와 실제 픽업·하역. 기존 7개 native command는 유지한다.
- 제목: **상자 하나를 옮기는 데도 여러 단계가 필요하다.**
- 본문: **요청이 들어오고, 차량이 선택되고, 목적지까지 이동합니다. 한 번의 운송은 여러 상태 전이가 연결된 결과입니다.**
- UX: 7번의 필수 클릭 대신 4개 관찰 묶음 **요청·배차 / 빈 차 이동 / 픽업·적재 운송 / 하역 완료**로 요약. 각 묶음의 네이티브 command 경계/가드 유지. **전체 자동 관찰**, **단계별 보기**, **다시 보기**를 제공. 동작의 실제 상태가 관찰되기 전에 다음 단계로 넘어가거나 엔진 타임라인을 순간이동시키지 않는다.
- 용어: 처음 등장 시 작은 주석으로 FOUP(보호 용기), OHT(운송 차량), MCS(물류 제어)만 설명.
- 선택 심화: Request lifecycle, Port service, FOUP ownership, immutable snapshot.

### Scene 04 — 0.5초씩 흐르는 시간
- 화면: Scene 03의 네이티브 화면·상태를 우선 이어서 보여준다. 단, 현재 TutorialCommandLayer의 명령 경계상 안전한 임의 1-Tick 진행이 불가능하면 **검증된 Snapshot을 복원한 별도 네이티브 실험 상태**에서 설명하며, 화면에 시나리오 전환을 짧게 명시한다. 실제 엔진 시각과 Request/Vehicle 상태를 읽고, 렌더러 보간과 엔진 Tick을 구분한다. 엔진/튜토리얼 가드를 우회하지 않는다.
- 제목: **시뮬레이션의 1초는 어떻게 흐를까?**
- 본문: **FAB FLOW의 엔진은 0.5초 단위로 상태를 갱신합니다. 같은 초기 조건이면 결과를 다시 확인할 수 있도록 설계했습니다.**
- 컨트롤: **재생 / 일시정지 / 한 Tick 진행 / 처음부터 다시 보기**. 한 Tick으로 눈에 띄는 이동이 없을 수 있으므로 실제 엔진 시각/상태 값을 함께 보여준다. 상태가 안 바뀌면 사실 그대로 표시한다.
- 선택 심화: 고정 Tick, seed, 결정성, wall clock vs simulation clock, snapshot/replay. 속도 버튼은 물리 속도 증가로 설명하지 않는다.

### Scene 05 — 가장 짧은 길이 정답일까?
- 화면: 기존 Work6 routeStudy/Engine decision/원본 route highlight를 재사용. 하나의 원본 3D 레일망 위에 **실제 선택 경로 / 합법적 대안 / 함께 보기**.
- 제목: **가장 짧은 길이 항상 좋은 길일까?**
- 본문: **거리만 보면 가까운 길이 유리합니다. 하지만 기다림까지 고려하면 경로를 평가하는 기준이 달라집니다.**
- 주의: routeStudy의 대안이 일부 링크 제거 가정에서 나왔다면 반드시 그 사실을 밝힌다. 이를 네이티브 MCS가 실제 선택한 경로나 DBR/CBR 실측 결과로 둔갑시키지 않는다.
- 선택 심화: Weighted Dijkstra, DBR 거리 비용 / CBR 혼잡 추정 비용, 노드에서의 합법적 재탐색, 추정치 ≠ 도착 보장.
- 컨트롤: 경로 보기 토글만. **실제 경로를 강제로 바꾸지 않는다.**

### Scene 06 — 모두 움직이는데 왜 막힐까?
- 화면: 기존 usePressureWorld의 **실제 Large V6 혼잡 및 대기 사례**. 그리드 전체 → 대기 중인 OHT·점유 레일로 시선 유도. 기존 Traffic view/heatmap 및 상태 신호만 활용.
- 제목: **모든 차량이 규칙대로 움직이는데, 왜 멈출까?**
- 본문: **차량들은 레일과 교차로를 함께 사용합니다. 다른 차량이 구간을 점유하면, 이동 가능한 길이 있어도 기다려야 합니다.**
- 컨트롤: **전체 흐름 / 대기 구간** 한 개. 숫자가 있는 경우 Native Engine의 현재 시각과 지표임을 명시한다.
- 선택 심화: exclusive section, 예약, wait-for cycle, deadlock 탐지·복구. **대기 차량 ≠ 확인된 Deadlock**. 실제로 cycle을 검증하지 못했다면 화면에 deadlock이라고 표시하지 않는다.
- 실제 혼잡 재현 준비가 실패하면 지어낸 정체 장면 대신 안내/다시 실행/검증된 정적 엔진 캡처로 gracefully degrade한다.

### Scene 07 — 더 복잡한 판단이 항상 좋을까?
- 화면: 3D FAB를 유지한 채 검증된 같은 조건 실험의 작은 비교 레이어. 비교 지표는 **완료 운송 수**, **미완료 수** 2개로 제한. 사용자가 두 정책 결과를 선택 가능하나, 동일 시각의 실제 Snapshot이 없으면 시뮬레이션 화면 전환으로 위장하지 않는다.
- 제목: **혼잡까지 계산하면 반드시 더 나을까?**
- 본문: **더 많은 정보를 사용해도 늘 좋은 결과가 나오지는 않습니다. 그래서 같은 조건에서 실제로 실행하고 비교해야 합니다.**
- 실증 예시: fab_flow/docs/operational/RESULTS.md, seed 17, 48 OHT, 8 requests/min, 당시 Engine operational 2.1의 총 1,800 simulation seconds. **DBR 131/240 완료(109 미완료) / CBR 130/240 완료(110 미완료)**. 이는 **과거 operational 2.1 버전에서 검증한 비교 결과**이며, Work6의 현재 Large V6 화면에서 실시간 실행한 값이 아니다. 비교 카드에 '검증된 이전 모델 실험'과 관찰 조건을 명시하고, 배경의 Live FAB 화면을 결과 Snapshot인 것처럼 보여주지 않는다. 가능하다면 개발 중 현재 Work6 Native V6의 동일 조건 자료로 대체하되, 값과 출처는 반드시 검증 후 변경한다. 차이 1건은 우열의 일반적 증거가 아니다.
- UX: **DBR 보기 / CBR 보기** 또는 **함께 비교**. 시각화는 기존 3D 뒤에 간결한 실측 수치만; 복잡한 대시보드로 만들지 않는다.
- 선택 심화: 동일 입력 보증, pending/unfinished의 차이, 관찰 종료 시점, seed·horizon·KPI가 중요한 이유, 계산 성능과 운영 성능 구분.

### Scene 08 — 화면 뒤의 세 가지 역할
- 화면: 마지막까지 동일 FAB FLOW 3D 세계를 보여준다. 실제 움직이는 OHT 위에 순차적으로 **Engine: 규칙을 계산 / State: 지금의 결과 / Three.js: 눈에 보이게 표현** 세 개의 짧은 주석을 둔다. 별도 건물 모형, 새 3D 계층도, 의도 없는 UI 카드 없음.
- 제목: **움직이는 화면 뒤에는 서로 다른 역할이 있다.**

## 6. 정보·UI·인터랙션 디자인
- 데스크톱: 원본 3D가 대략 65~75% 시각적 주인공. 설명은 왼쪽/아래 한 영역에 1~2문장. 시점과 주석이 객체를 가리지 않도록 앵커 조정.
- 모바일 가로: 3D 우선, 설명 패널은 접기/펼치기 및 안전 영역 내 배치. 본편 기본 설명으로 화면의 대부분을 막지 않는다. 모바일 세로: 핵심 현상을 확대하고 짧은 하단 패널. 전체 장면의 세로 내장 스크롤 강요 금지.
- 제목·본문은 읽기 쉬운 실제 픽셀 크기로 검증한다(권장: 데스크톱 제목 28~38px, 본문 16~18px; 작은 화면 본문 14~16px; 필수 라벨 12px 미만 금지). 3D 공간 안의 아주 작은 레이블은 필수 설명에 사용하지 않는다.
- 정보 위계: **질문 / 실제 현상 / 관찰 결과 / 조금 더 깊게**. 전환 중 글자를 숨기지 않는다. 장면별 최대 주요 컨트롤 한 종류(선택 그룹 포함).
- 01→08은 **좌/우 화살표 및 하단 이전/다음**으로 명시적 이동, H 홈. 텍스트 입력/Drawer 안에서는 단축키가 조작을 가로채지 않는다. Esc로 Drawer 닫기. Space 재생/정지는 포커스 안전조건에서만.
- 예전의 v2.2 단층 Large 중심 **시각적 연속성**을 유지한다. 여러 Scene이 동일한 3D 레이아웃과 렌더러를 재사용하더라도 Native Engine/seed/시간은 다를 수 있다. **화면이 이어진다고 실제 한 운송의 연속이라고 암시하지 않는다.** 시나리오가 바뀌면 간결하게 표시한다.
- 자동 카메라 연출은 수동 제어 시 중단. Replay/Skip/Reduced Motion 제공. 모션이 꺼졌을 때도 상태·설명 읽기 가능.
- 심화 정보는 기본 숨김, 항목당 150~250 한국어 자 내외의 설명 + 실제 코드 근거(필요할 때만). 기술 상세용 Drawer는 별도 스크롤 허용하되 기본 서사에서 중첩 스크롤을 만들지 않는다.
- 종료는 실제 FAB FLOW 링크 CTA 1개, 필요하면 **처음부터** 보조 버튼. 불필요한 가입·퀴즈·사이드 패널 복제 없음.

## 9. 설계상 트레이드오프
- 복잡한 의사결정/Deadlock/정책을 전부 설명하지 않고, 대표 관찰 한 번과 선택적 심화로 압축한다.
- 완전한 FAB FLOW 앱을 다시 포장하지 않는다. 원본 실행 화면을 이용해 각 기술 개념에 **조명**을 비추는 웹 에세이로 만든다.
- 기술 자료로서 진짜 코드를 근거로 하되, 사용자에게 소스 파일 설명을 강요하지 않는다.
- 네이티브 이동 시각화가 독자의 이해보다 오래 걸리면 관찰 경계에서 일시정지/건너뛰기를 허용한다. 엔진 시계를 임의 점프시키거나 가짜 이동으로 대체하지 않는다.

## 10. v3.1 확정 — 기존 Work6 보존 및 구현 우선순위
- **전면 삭제·빈 스캐폴드 재생성 금지.** 이전 11개 Scene은 Git 기준 커밋에서 언제든 재현 가능해야 하고, 이 리워크는 현재 `projects/fab-flow/` 소스에서 점진적으로 이루어진다.
- 먼저 기존 시각화와 엔진 기능을 새 Scene에 연결한다. 주요 기능(네이티브 픽업/하역, 2.7초 규모 공개, Native 경로 선택, Large 혼잡, 카메라, 정적 Pages 빌드)의 검증이 통과하기 전에는 기존 구현을 제거하지 않는다.
- **8 Scene은 본편의 목표 구조**다. 구현 중 기존의 잘 된 연출을 잃는 것보다 더 중요한 것은 내용의 이해와 품질이며, 장면 내 하위 비트로 충분히 보존할 수 있다. Scene 수를 채우려 새 기능을 만들거나, 숫자에 맞추려 좋은 시각화를 폐기하지 않는다.
- 각 기능은 **재사용 → 설명/카메라/주석만 변경 → 필요한 인터페이스 최소 확장** 순서로 해결한다. 불필요한 대체 3D 제작, 엔진 포크 변경, 새 프레임워크 도입을 하지 않는다.
- 운영 실험·렌더링 시각화·튜토리얼은 **서로 다른 Native 시나리오**일 수 있다. 같은 FAB 3D를 쓰는 사실과 같은 입력/결과라는 사실을 혼동하지 않는다.
- 명시된 품질 게이트 이전에는 `projects/fab-flow/`를 통째로 삭제하지 않고, 구버전의 작동 가능한 콘텐츠를 임의로 덮어쓰지 않는다.
- **문서 우선순위:** 이 문서(v3.1 최종 콘텐츠·디자인) → [개발 계획](work6-engineering-development-plan.md)(실행·파일·검증) → [reuse contract](reuse-contract.md)(Native 불변 조건) → [기존 master plan](work6-master-plan.md)(역사). 코드와 불일치하면 현재 코드/엔진의 사실을 먼저 감사하고, 기술 제약을 숨긴 채 이야기를 조작하지 않는다.
