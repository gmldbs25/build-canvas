## 콘텐츠가 전달하는 한 문장

**거대한 반도체 FAB의 물류는 한 대의 OHT에서 시작하지만, 수많은 운송과 의사결정이 동시에 얽혀 움직이는 시스템이다.**

## 화면 공통 문법

### 도메인 입문 규칙 (2026-10-30 확정)

**관람자 가정:** 웨이퍼·반도체 공정·OHT·MCS·FOUP·FAB 용어를 모른다. 본편은 전문 용어를 먼저 제시하고 풀이하지 않는다.

- Scene01에서 먼저: '반도체가 완성되기까지 여러 장비를 거친다'를 영상/실제 공장 3D 안에서 느끼게 한다. 반도체 제조 공정 자체는 시뮬레이션하지 않음.
- Scene02에서: 웨이퍼(반도체가 만들어지는 얇은 원판) → FOUP(웨이퍼를 담아 보호하는 전용 용기) → OHT(용기를 들어 옮기는 천장 차량) → Port(장비가 용기를 주고받는 자리) 순으로 짧게 관찰한다.
- Scene03에서: **한 번의 운송 요청이란 공정 장비로 '가공하라'는 명령이 아니라 '여기에 있는 FOUP를 다음 장비로 옮겨 달라'는 물류 요청**이라는 점을 입문 설명으로 명시한다. 실제 FAB FLOW는 이동·차량·배차·경로를 계산하며 제조 공정 실행은 모델링하지 않는다.
- 'MCS'는 반드시 '어떤 차량이 옮기고 어떤 길로 가는지 관리하는 시스템'을 먼저 보여주고 이름을 붙인다.
- 화면 설명은 '상황 → 변화 → 이유 → 다음에 볼 것'으로 짧게. 복잡한 수치/코드/전문 용어는 선택형 기술 심화로 분리한다.
- 클릭 후 엔진 결과를 관찰할 **안정적인 정지 상태**를 제공한다. 버튼을 누르자마자 다음 장면/다음 학습 단계로 자동 전환하는 UX 금지.
- 3D 세계의 FOUP/Port/OHT를 가능한 실제 오브젝트에 연결해 강조한다. 실물로 오해받을 추상 도형 애니메이션을 제작하지 않는다.
- **출처**: Samsung Foundry FAB Automation (https://semiconductor.samsung.com/foundry/manufacturing/fab-automation/), 연구(https://www.mdpi.com/2227-7390/13/7/1167), Samsung SDS MES Material Control (https://image.samsungsds.com/us/resources/__icsFiles/afieldfile/2017/01/18/Nexplant_MES_PT_Eng.pdf).

- 무대: 실제 FAB FLOW의 `ThreeFacilityScene` 및 Native Engine에서 나온 Three.js 세계. 별도의 SVG/CSS OHT 재현 금지.
- 텍스트: 기본은 제목 1개 + 설명 1~2문장. 화면보다 설명이 앞서지 않게 한다. 보조 정보는 필요한 순간만 등장.
- Navigation: 전/후 버튼 및 좌우 화살표. `H`는 홈으로. 각 Scene의 타임라인·버튼과 장면 이동 키가 충돌할 때 내부 조작 우선.
- 카메라: 원본 `fabCamera`·렌더러 동작을 우선 사용. 관람자 수동 조작은 자동 카메라를 취소. Scene 이동은 **사용자가 명시적으로** 입력.
- 타입: `C` Cinematic full-bleed, `E` Editorial split, `I` meaningful interaction. 기본 C이며 설명 복잡도가 높은 곳만 E.
- 본편에서는 "플로팅 KPI 카드 3개" 등의 반복 장식을 사용하지 않는다.
- 실제 렌더러 재사용 검증 실패 시 도형으로 대체하지 말고 오류·개발 중 상태를 분명히 표시한다.
- 삼성 평택캠퍼스는 현실 규모의 레퍼런스. 실제 삼성 내부 지도라 오해될 배치도·크기 수치·연결 애니메이션을 사용하지 않는다.

## Chapter 01 — FOLLOW (국소적인 관찰)

### S01 · 공장 안에도 교통체증이? · C
- **화면 카피:** "반도체는 한 대의 장비에서 완성되지 않는다." / "여러 장비를 거치는 동안, 이 작은 차량은 무엇을 할까?"
- 경험: 차량 한 대를 먼저 보여주되, '이동이 필요한 이유'를 생활 언어로 짧게 전달한 뒤 이동 수단에 주목한다. '교통체증'은 차량과 레일에 익숙해진 후 다시 제시한다.
- 3D: OHT 한 대를 근접 Follow. 실제 레일과 장비는 주변에 부분적으로만 보인다.
- 카메라: close OHT → 근접 시설 노출. 첫 장면에서 전체 FAB를 보여주지 않음.
- 자료: FAB FLOW의 실제 OHT·FOUP·조명과 `confirmedMotion` 기반 이동.
- UX: 클릭 없이 관찰. 사용자는 타이밍과 관계없이 다음 장면으로 이동 가능.

### S02 · 무엇을 옮기는 걸까? · E
- **카피:** "얇은 원판인 웨이퍼를 보호하는 상자가 있어요." / "이 상자(FOUP)를 천장 차량(OHT)이 다음 장비까지 옮겨 줍니다."
- 교육 순서: 웨이퍼의 일상어 정의 → FOUP 실물 강조 → 실제 OHT 실물 강조 → 장비가 상자를 주고받는 Port 순서. 이름만 외우게 하지 않는다.
- 3D: 실제 FOUP·OHT·Port를 같은 시야 안에 확대. 순서대로 대상 강조.
- 설명 레이어: 짧은 객체 이름 주석, 필요시 FOUP/Port 뜻만 선택적으로 펼치기.
- 개념: 웨이퍼/FOUP/OHT/Port. Stocker는 필요한 후속 장면에서 소개.

### 단계적 규모 공개·운송 경로 시각화 (2026-10-30 확정)

- **초기 Scene 01–03은 실제 FAB FLOW 3D를 가까이서 관찰하는 '국소 세계'로 제한한다.** 초기 운송 중 휠 줌아웃, 핀치 줌아웃, 전체 보기, 드래그 이동 등의 우회 조작으로 전체 FAB를 미리 노출하지 않는다. Scene 04에 들어가면 전체 보기·줌·팬을 활성화한다.
- **첫 운송은 가능한 한 같은 Bay 안 가까운 장비 사이의 짧은 이동**으로 구성한다. 정확한 네이티브 FAB FLOW 레일 방향/경로에서 유효한, 고정 seed 기반 재현 가능한 시나리오를 선택한다. 실제 선택 경로가 길어지지 않는지 브라우저 로그와 엔진 상태로 검증한다.
- 출발 차량이 배정된 뒤, 이동 전후 **실제 MCS가 계산한 선택 경로를 원본 레일 위에 강조 표시**한다. '빈 OHT가 가지러 가는 경로'와 'FOUP를 실어 나르는 경로'를 네이티브 명령 단계에 맞춰 보여준다. 예상 경로를 임의 제작하거나 단순 직선으로 그리지 않는다.
- 경로 강조선은 OHT와 레일을 가리지 않는 선명한 색/두께로 표시한다. 장면 설명은 짧은 안내('실제 OHT 이동 경로') 중심.
- Scene 04의 Camera Follow → Bay → Whole FAB가 **처음으로 공장 전체 규모를 공개하는 순간**이 되도록 한다. 레일 위치와 실제 세계는 그대로 연속 유지하고, 3D를 재구현하지 않는다.
- 초반 경로의 길이·실제 선택 링크·줌 제한·Scene 04 잠금 해제·원본 3D 사용을 자동화 회귀 테스트에 넣는다.

### 실제 장면 검토: FOUP 등장·운송 동선·하역 (2026-10-30)

- **운송 요청 직후 FOUP 등장:** 실제 Native Engine이 요청을 생성한 뒤 FAB FLOW의 원본 노란 FOUP 모델만 부드럽게 나타나게 한다. 전체 Three.js World/Canvas를 번쩍이며 교체하거나 다른 가짜 상자를 덧그리지 않는다.
- **초보자가 보기 쉬운 운송 동선:** 같은 Bay의 가까운 장비뿐 아니라, **일방통행 레일을 따라 계산한 실제 경로 길이 / 직선거리의 비율**도 함께 평가하여 큰 우회가 생기는 예시는 피한다. 시나리오 seed만 선택하며 MCS 라우팅과 레일 연결 규칙은 변경하지 않는다.
- **FOUP 픽업·하역:** Native Engine의 0.5초 Tick와 FOUP 소유권은 그대로 유지하고 Work6 재생 속도를 천천히 조절한다. 위치는 Native Tick 간 높이를 보간하되, 연출만으로 실제 상태를 먼저 확정하지 않는다.
- **하역 후 화면 유지:** Stage 03에서 하역이 끝나면 갑자기 Bay/Whole로 줌아웃하지 않는다. FOUP가 내려진 모습을 가까이서 관찰한 후 관람자가 Scene 04로 진행할 때에만 규모 공개 연출이 시작된다.
- 브라우저 자동화로 첫 요청 생성, 실제 3D/Native 운송, 픽업, 하역 완료, close-up 카메라 유지, 다음 Scene에서만 줌 해제를 검증한다.

### S03 · 한 건의 운송 · I **프로토타입 핵심**
- **도입 카피:** "다음 장비로 웨이퍼를 보내야 합니다." / "웨이퍼를 담은 FOUP를 옮기기 위해, 공장 물류 시스템에 이동을 부탁해 볼까요?"
- **일상적 시나리오 전제:** 앞선 공정을 마치고 다음 장비로 이동해야 하는 상황을 *교육상 가정*한다. FAB FLOW의 Native Engine에는 '공정 완료' 이벤트가 없으므로 완료 상태가 실제로 계산된 것처럼 표시하지 않는다.
- **중간 단계와 관람자의 이해:**
  | Engine command | 누르기 전 의미 | 실제 실행 후 보여줄 상태 | 쉬운 행동 이름 |
  |---|---|---|---|
  | request | 옮길 필요가 있다 | 물류 요청이 접수되었고 아직 차량은 선택되지 않았다 | 다음 장비로 보내기 |
  | dispatch | 어떤 차가 맡을까? | OHT 한 대가 *배정*되었다(여기서 '배차' 소개) | 담당 차량 정하기 |
  | empty-travel | 차량은 출발지에 없다 | 빈 OHT가 FOUP를 가지러 간다 | 빈 차량 이동 보기 |
  | pickup | FOUP는 출발 Port에 있다 | OHT가 FOUP를 싣는다 | 상자 싣기 보기 |
  | route | 어디로 운반해야 할까? | 엔진이 실제 목적지 경로를 선택한다 | 이동 경로 살펴보기 |
  | loaded-travel | 차량이 FOUP를 싣고 있다 | 실제 레일을 따라 목적지까지 간다 | 목적지로 이동 보기 |
  | dropoff | 목적지 Port에 도착했다 | FOUP를 내려놓고 운송을 완료한다 | 상자 내려놓기 |
- **UX:** 클릭 전 간단한 이유 설명. 클릭 후 실제 Native 상태를 유지하면서 "방금 달라진 것"을 설명한 다음 **사용자의 다음 버튼**을 기다린다. `request` 클릭과 동시에 `dispatch` 실행 금지. 전체는 하나의 Scene, 클릭·설명 7단계이지 7 Scene이 아니다.
- **점진 용어 소개:** 첫 단계의 '운송 요청'은 쉬운 말 뒤에 짧게, '배차'는 선택된 차량을 보고 나서, 'MCS'는 차량·경로 판단을 설명할 때, `Tick/Policy` 수치는 숨겨진 상세 보기.
- 하위 단계의 Native 명령: request → dispatch → empty-travel → pickup → route → loaded-travel → dropoff.
- 3D: `createTutorialWorld`·`TutorialCommandLayer`·`Engine` + `ThreeFacilityScene`.
- 행동: 사용자가 핵심 운송 단계를 넘기며 실제 엔진 결과를 본다. 내부 단계는 필요하면 통합 진행 가능.
- 검증: 실제 request ID·vehicle ID·source/destination Port·FOUP 소유권, 이동·픽업·하역.
- 실패 금지: 고정한 차량을 임의 경로에 움직이는 CSS 키프레임/가짜 재생.

## Chapter 02 — REVEAL (규모와 판단)

### S04 · 보이지 않던 전체 · C **프로토타입 핵심**
- **카피:** "지금까지 본 건 공장의 극히 일부였다." / "이런 운송이 수많은 장비 사이에서 동시에 일어난다면?"
- 3D: **같은 FAB FLOW 장면을 유지**하며 Follow → Bay → Whole FAB 순서로 줌아웃.
- 연출: 긴 설명·숫자·카드 없이 스케일 변화에 집중.
- 현실성: 삼성 평택의 공개 규모와 Work6 모형은 별개임을 주석에서 명시. 실제 평택 내부 재현을 주장하지 않음.
- 조작: 관람자 카메라 우선·건너뛰기 가능. 하드 컷을 반복해 서로 다른 세계처럼 보이게 하지 않음.

### S05 · 정해진 길 위에서 · E
- **카피:** "차량은 아무 길로나 갈 수 없다." / "방향이 정해진 레일 위에서 경로가 연결된다."
- 3D: 실제 방향성 레일에 경로 강조. Node/Link/Port는 이해를 위해 선택적 주석으로 소개.
- 개념 그래프는 별도 보조 설명에 허용. FAB 실사 대체 금지.

### S06 · 누가 결정할까? · I **프로토타입 핵심**
- **카피:** "운반할 차는 누가 고를까?" / "어느 길로 가야 빠르게 도착할까?"
- 선행 설명: 먼저 Scene03에서 관찰한 차량의 선택과 경로를 다시 보여준다. 이 판단을 관리하는 시스템을 여기서 처음 **물류 제어 시스템(MCS)**으로 명명한다. 경로 정책/거리·혼잡 가중치는 선택형 기술 심화로 분리한다.
- 인터랙션: (1) 후보 차량·운송 요청 관찰 (2) 배차/경로의 차이 안내 (3) 실제 `inspectDecision` 등으로 얻은 경로 후보/비용과 선택된 경로 표시.
- 실제 OHT·Port·Rail과 *엔진에서 나온 동일한 그래프*로 경로 오버레이.
- 주의: 별도 장식용 route line이나 `CBR 항상 승리` 연출 금지. 결과 확인 전에 동일 시나리오/버전이 맞는지 검증.

## Chapter 03 — PRESSURE (현상이 시스템이 되는 순간)

### S07 · 흐름이 멈추는 순간 · C
- **카피:** "앞의 OHT가 멈추면 뒤의 차량은?" / "같은 공간은 동시에 무한히 사용할 수 없다."
- 실제 점유·대기/장애에서 움직임이 멈추는 시점 강조. 관람자는 관찰.
- 막힘의 원인을 단정하지 말고 실제 상태 진단과 대응한다.

### S08 · 무엇을 측정할까? · E
- **카피:** "움직이는 차량이 많다고, 물류가 잘 흐르는 것은 아니다." / "완료량과 미완료 요청, 소요 시간을 함께 보자."

### 구현 시 유의
- 원본 `src/components/ThreeFacilityScene.tsx`는 광범위한 내부 의존성을 가짐. `src/sim`은 상태·경로·결정성의 정본. 복사한 모듈을 재해석한 빈 껍데기로 사용하지 말 것.
- Build Canvas는 GitHub Pages 정적 사이트. Next.js 의존 컴포넌트·경로 alias·Three.js 자원을 별도 프로젝트로 옮길 때 Vite 정적 빌드 경로/버전을 먼저 검증.
- **PoC가 실제 원본 3D를 사용하지 못하면 개발 완료로 표시하지 않는다.**
- 시각적 성공 기준은 최종 이미지를 사람이 눈으로 보는 검토. 테스트 통과만으로 사용자 승인을 기록하지 않는다.
