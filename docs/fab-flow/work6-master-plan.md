# Work 6 — FAB FLOW / 콘텐츠·디자인 마스터 플랜

> Status: PLANNING · v0.3 · 2026-10-30
>
> 이 문서는 Build Canvas Work6의 현재 합의 사항을 누적 관리한다. 구현·배포 승인 문서는 아니다. 내용/디자인/기술 결정의 **확정/제안/미결정** 상태를 혼동하지 않는다.

## 1. 프로젝트 목적 (확정)

- 위치: `gmldbs25/build-canvas`의 **Work 6**. 실제 프로젝트 소스는 구현 시 `projects/fab-flow/`, 콘텐츠/설계는 `docs/fab-flow/`을 기준으로 한다.
- 대상: FAB 물류에 익숙하지 않은 반도체 신입 엔지니어, 비전공자, 물류/소프트웨어 엔지니어.
- 목표: 한 대의 OHT와 하나의 FOUP에서 출발해 실제 FAB 물류의 복잡성과 배차·경로·혼잡·운영 의사결정을 이해시키고, 마지막에 웹 시뮬레이터 FAB FLOW로 연결한다.
- 작품 성격: **실시간 3D를 사용한 인터랙티브 기술 다큐멘터리**. FAB FLOW 기능 설명서, 일반 텍스트 아티클, 제품 광고, 제작 일기가 아니다.
- 기본 서사: 질문 → 직접 관찰 → 발견 → 다음 질문. 관람자가 제어권을 갖고 진행한다.
- 단일 통합 경험: 프레젠테이션/아티클 모드를 나누지 않는다. 핵심 설명은 본문에서 이해 가능해야 하며 기술 심화는 선택적으로 열 수 있다.

## 2. 현실 규모와 모델의 경계 (확정)

- **삼성전자 평택캠퍼스**를 대형 반도체 제조시설의 현실적 규모감 레퍼런스로 사용한다.
- 캠퍼스 전체 규모, 개별 FAB 건물, 특정 층의 물류망을 동일한 대상으로 취급하지 않는다.
- 공개된 사실·출처와 교육용 추상화·제작자의 해석을 구분한다. 비공개 내부 설계도나 실제 평택 OHT 네트워크를 재현했다고 주장하지 않는다.
- 관람자의 시야를 **한 공정 장비/OHT → Bay → 여러 Bay → 넓은 FAB 물류망**으로 확장한다.
- FAB FLOW의 Small/Medium/Large 및 개발 중인 Multi Large는 **계속 발전 중인 교육용 시뮬레이터**다. Work6를 위해 평택 규모의 전체 네이티브 엔진을 새로 구현하지 않는다.
- 실제 시뮬레이터보다 큰 배경의 개념적 규모 연출을 사용한다면 작동 중인 엔진 영역과 명확히 구별한다.

## 3. 구성 (11 scenes · 4 chapters / 1차 기준 확정)

각 Scene은 페이지 분할 단위이며 조작 횟수나 하위 단계를 제한하지 않는다. 개별 Scene 내부에서 여러 단계로 진행할 수 있다.

| Chapter | Scene | 제목/질문 | 관람자가 경험할 핵심 |
|---|---:|---|---|
| 01 FOLLOW | 01 | 공장 안에도 교통체증이? | OHT 한 대의 실제 움직임으로 시작 |
| 01 FOLLOW | 02 | 무엇을 옮기는 걸까? | 웨이퍼·FOUP·OHT·Port의 관계 |
| 01 FOLLOW | 03 | 한 건의 운송 | 요청 → 배차 → 빈 차 이동 → 픽업 → 경로 → 적재 운송 → 하역 |
| 02 REVEAL | 04 | 보이지 않던 전체 | 국소 구역에서 Bay/네트워크로 카메라 확장; 규모감 공개 |
| 02 REVEAL | 05 | 정해진 길 위에서 | 방향성 Rail·Node·Link·Port·Bay |
| 02 REVEAL | 06 | 누가 결정할까? | MCS 배차와 경로 선택의 차이; 조건에 따른 경로 |

| 03 PRESSURE | 09 | 운영을 바꿔본다면? | 수요·OHT 수·경로 정책 예측과 실제 비교 |
| 04 BEHIND | 10 | 화면 뒤의 시스템 | 0.5초 엔진 Tick, 상태·MCS·Three.js 분리 |
| 04 BEHIND | 11 | 이제 당신의 FAB | 실제 FAB FLOW 앱으로 연결 |

### 내러티브 운용
- 장면 01~03: 거대한 FAB 전체를 먼저 노출하지 말 것. 국소적인 운송의 역할부터 이해시킨다.
- 장면 04: 작품의 첫 번째 대표 장면. OHT Follow에서 시작해 Bay/전체 물류망까지 확장하는 시네마틱 공개.
- 장면 03·06·09에서만 조작을 상대적으로 강조한다(한 건의 운송, MCS 판단, 운영 실험). 07·08을 포함한 나머지 장면은 주로 실제 동작을 관찰하면서 이해하도록 하고, 모든 장면에 클릭 미션을 억지로 추가하지 않는다.
- 장면 09: 특정 정책이 무조건 우수하다고 가정하지 않는다. 같은 입력 조건의 **실제 검증된 비교 결과**만 사용한다.
- 장면 10: 개발자가 원한다면 엔진/모션/렌더러와 결정적 실행 방식의 기술 심화 패널 제공.
- 장면 11: FAB FLOW의 실제 진입 링크는 배포 주소 확인 뒤 확정한다.
- Multi Large의 층간 물류/Lifter는 구현 안정화 후 **추가 관찰 요소/심화 연출**로 평가한다. 아직 11개 Scene의 본편 필수 요구로 고정하지 않는다.

## 4. 디자인 언어 (화면 구성 1차 확정 · 세부 시안 검증 필요)

### 디자인 결정 1 — 3D 중심 레이아웃 (확정)

- **A안 확정:** FAB FLOW의 실제 3D 화면이 화면 대부분을 차지하는 **몰입형 3D 중심** 구성으로 설계한다.
- 기술 설명과 비교 정보가 많아지는 장면에서만 **B안(텍스트/3D 분할형 Editorial)**을 부분 적용한다.
- 실시간 OHT·FOUP·장비·레일은 원본 FAB FLOW 코드 재사용 계약을 따른다. 설명을 위해 같은 모델을 도형으로 다시 그리지 않는다.
- 본 결정은 전체 Scene의 기본 화면 구성에 적용한다. 장면 이동과 조작 비중은 아래 디자인 결정 2·3을 따르며, 설명은 간결한 본문 + 선택적 기술 심화를 기본값으로 한다.

### 프로토타입 검토에서 확인한 작품 정체성 (확정)

- **FAB FLOW와 Work6의 시각적 통일감은 의도적으로 유지한다.** FAB FLOW 첫 진입 화면과 닮은 원본 3D 세계는 단점이 아니라, 실제 시뮬레이터를 웹 자료에 녹였음을 보여주는 근거다.
- Work6의 목표는 시뮬레이터를 닮은 연출 영상이나 모형을 만드는 게 아니다. **실제 시뮬레이션 엔진의 상태·계산·모델·움직임을 바탕으로 그 의미를 관찰하고 이해하는 경험**이다.
- 차별화는 세계 자체의 스타일 교체가 아니라 **카메라 구도, 정보 공개 순서, 설명 타이포그래피, 실제 상태에 연결된 강조, 의미 있는 인터랙션**에서 만든다.
- Work6에서 본 OHT·FOUP·MCS·Rail의 세계가 마지막 FAB FLOW 앱에서도 동일하게 이어지는 **이해 → 실제 운영**의 연속성을 지킨다.
- 따라서 Work6만의 외관을 억지로 만들려고 원본의 재질·색상·장비 형상을 재해석하거나, 조작 패널을 불필요하게 복제하지 않는다. 시뮬레이터와 콘텐츠의 UI 역할은 구분한다.

작업명: **The Factory Atlas / Editorial × Engineering × Cinematic**. 최종 화면 제목은 미확정.

- FAB FLOW의 기존 따뜻한 미니어처 팔레트(아이보리 바닥, 민트·화이트 장비, 짙은 레일, 앰버 FOUP)를 유지한다.
- 웹 다큐멘터리/산업 디자인 전시물 같은 편집감: 큰 화면에서 정확한 타이포그래피, 여백, 엔지니어링 주석, 의미 있는 카메라 전환.
- 장면 성격에 따라 **Cinematic / Editorial / Interactive** 구성을 바꾼다. 11개 화면을 동일한 카드 템플릿으로 찍어내지 않는다.
- 주석과 강조선은 되도록 실제 객체·레일·운송 상태에 연결하고, 맥락 없이 아이콘/카드를 추가하지 않는다.
- 원색 네온, 과도한 글로우/그라데이션, 읽기 어려운 극소 글씨, 반복되는 텍스트 등장 효과, 의미 없는 장식 아이콘을 피한다.
- 실제 FAB FLOW 세계를 근거 없이 어둡고 사실적인 SF 공장으로 재해석하지 않는다.
- 강한 장면 전환은 **시야 확장/실제 운송/판단 전환에 의미가 있을 때만** 사용한다.

## 5. 인터랙션·UX (확정 원칙)

### 디자인 결정 4 — 도메인 지식 0인 관람자 기준 (확정)

- **최우선 대상은 반도체/제조/물류 경험이 전혀 없는 관람자다.** 전문가는 세부 기술을 펼쳐서 볼 수 있지만, 본편을 이해하는 데 선행지식을 요구하지 않는다.
- **용어보다 이유가 먼저:** `다음 제조 작업을 위해 이동이 필요하다 → 웨이퍼를 보호 용기(FOUP)에 담는다 → 운반 차량(OHT)을 골라 움직인다 → 목적지 장비에 전달한다` 순으로 소개한다. 처음 등장하는 용어는 일상 언어 한 줄 풀이와 함께 제공한다.
- **운송 요청의 의미:** 생산·공정 일정에 따라 장비 간 이동이 필요할 때 물류 쪽에 '이 FOUP를 출발지에서 목적지로 옮겨 달라'고 요청하는 사건이다. '공정 작업 명령 = OHT 운송 요청'으로 설명하지 않는다. Work6의 네이티브 엔진은 **물류만** 시뮬레이션하므로 공정 장비가 실제로 웨이퍼를 가공/완료한 것처럼 묘사하지 않는다.
- **한 번에 변화 하나:** '운송 요청' 버튼을 누르면 요청이 등록된 상태를 명확히 관찰하고, '배차'는 그 다음에 차량이 선택되는 별개의 사건으로 관찰한다. 클릭 즉시 의미 있는 중간 상태를 스쳐 지나가는 자동 진행은 금지한다.
- Scene 03의 모든 단계는 **사전 맥락 → 사용자의 명시적 실행 → 실제 Engine 상태 변화 → 방금 무엇이 달라졌는지 해설 → 다음 행동**을 따른다. 엔진이 명령 경계를 만족할 때만 다음 단계를 제공한다. 원본 렌더링/상태 보존.
- 첫 화면에 `MCS`, `FOUP`, `OHT`, `Port`, `Tick`, `KPI`, `DBR/CBR`를 일괄적으로 나열하지 않는다. 핵심 진행 버튼은 사람이 이해하는 표현을 먼저 쓴다(예: **'다음 장비로 보내기'**). 정확한 전문용어는 해당 순간에 짧게 연결.
- 초보자용 제목/설명은 '무엇을 보고 있는지', '왜 지금 움직이는지', '누가 무엇을 결정했는지'에 답해야 한다. 시스템 이름이나 알고리즘 소개 자체가 화면의 목적이 아니다.
- 강제 퀴즈/긴 튜토리얼은 피한다. 깊이 선택은 접어둔 `자세히 보기`, 관찰/재생/장면 전환은 계속 가능하도록 한다.
- 검수는 **'반도체·물류를 처음 접한 사람이 전문용어 암기 없이 한 번의 운송을 친구에게 설명할 수 있는가?'**를 통과 기준으로 삼는다.

### 디자인 결정 3 — 관찰 중심, 핵심 순간만 직접 조작 (확정)

- **A안 확정:** Work6의 기본 경험은 FAB FLOW의 실제 3D 장면을 **관찰하며 이야기를 따라가는 방식**이다. 대부분의 Scene에서는 사용자의 조작을 진행 필수 조건으로 강요하지 않는다.
- 직접 조작의 핵심은 **Scene 03(실제 운송), Scene 06(MCS 배차·경로 판단), Scene 09(수요·Fleet·정책 실험)**에 집중한다. 상호작용은 관람자의 이해를 깊게 할 때만 추가한다.
- 기존 FAB FLOW의 실제 엔진과 3D 렌더러에서 나온 움직임이 장면의 주인공이며, 사용법 튜토리얼이나 미니게임으로 변질시키지 않는다.
- 사용자는 자동 진행 중인 **장면 안의 관찰 연출**을 건너뛰거나 다시 볼 수 있어야 한다. Scene 간 전환은 사용자 명시 입력을 기다린다는 결정 2를 유지한다.
- 설명은 장면당 핵심 문구 중심으로 간결하게 두고, 엔지니어링 세부는 선택적 펼치기로 제공한다(표현/분량은 시각 시안에서 검증).

### 디자인 결정 2 — 단계별 장면 전환 (확정)

- **A안 확정:** Scene 간 이동은 **다음/이전 버튼 및 키보드 좌·우 방향키**로 수행한다. 본편 전체를 세로 스크롤에 연동해 자동 이동하는 방식은 사용하지 않는다.
- 각 Scene 안에서는 실제 FAB FLOW 3D 애니메이션과 필요한 조작을 관찰/실행한다. 같은 공간에서 자연스러운 카메라 이동과 상태 전환을 제공해 단순 슬라이드 절단처럼 보이지 않게 한다.
- Scene 전환은 관람자가 명시적으로 제어한다. 재생 중인 시뮬레이션의 진행과 장면 이동은 구별한다.
- 장면 내 조작·입력 필드·모달·팝오버·세부 단계와 좌·우 방향키가 충돌할 때는 사용자 조작을 우선한다. 키보드 바인딩과 상세 우선순위는 실제 UI 구현에서 검증한다.

- 앞/뒤 Scene으로 이동할 수 있고 사용자의 명시적인 조작 없이 다음 Scene으로 자동 진행하지 않는다.
- Scene 안에 운송 단계가 있다면 별도의 단계 이동·다시 보기·중단/복구를 설계한다. 일부 단계의 엔진 제어를 관찰자가 실행하더라도 대부분의 Scene을 클릭 의무형으로 만들지 않는다.
- 관람자의 탐색은 키보드와 터치 환경을 지원한다.
- Build Canvas 공통 규칙: **H 키로 홈 복귀**, 텍스트 입력 중에는 무시.
- 자동 연출과 수동 카메라 조작이 충돌하지 않게 한다. 수동 개입은 자동 카메라를 중단한다.
- 모바일 가로, 일반 데스크톱, 작은 화면, Reduced Motion을 검증한다. 중요 설명이 3D 물체/패널 뒤로 가려지지 않는다.

## 6. FAB FLOW 실제 코드 재사용 (필수 구현 계약)

**가장 중요한 요구사항: Work6에서 OHT·FOUP·레일·장비·FAB 공간과 그 움직임을 표현할 때, `gmldbs25/fab_flow`에 존재하는 실제 Three.js 모델·렌더러·Geometry·Motion·시뮬레이션/튜토리얼 로직을 기술적 원본으로 사용한다.**

- 기존 OHT와 유사한 SVG/CSS 사각형·원/간략 박스 메시를 새로 그려서 대체하지 않는다.
- 녹화된 영상/가짜 루프 애니메이션을 기본 시각 구현으로 쓰지 않는다.
- 장면의 버튼은 필요한 경우 실제 Engine/Tutorial의 운송 상태를 진행시키며, 기존 Renderer가 그 상태를 실제로 표시하도록 한다.
- Work6가 소유하는 것은 콘텐츠/진행/타이포그래피/주석/인터랙션/카메라 연출 계층이다.
- 개념적인 알고리즘 도표·문서/통계 그래프에는 2D SVG나 HTML을 사용할 수 있으나, 이를 **실제 FAB 물류 애니메이션**으로 위장하지 않는다.
- 별도 저장소/프레임워크 간 재사용은 사전 기술 검증이 필요하다. 통째 앱 내장이나 독립적인 대체 렌더러 재작성을 기본 해법으로 삼지 않는다.
- 상세 준수 조건과 검증 범위는 [reuse-contract.md](reuse-contract.md) 참조.
